## Description

One point in the response from David's contact was about data retention. This highlights a need for a response (and implementation schedule necessary to first customer) that is more sophisticated than "best practices".

So a better response could be that our retention policy is adaptable to match the bank's policy and that we "have" (shall be in place in time for whatever we give them as their go-live date) these specific security features in place:

* this ticket is to really nail down some specific security guarantees and to take a full sweep through the code base to identify all the SECURITY TO-DO items and make tickets for them

## Comments

Discussing with David and Travis, we would like to say that we are NOT keeping any data beyond what is minimally necessary. Any outputs generated would be "printed" to file and exported that way so the banks can hold on to the input/output documents as long as they need. If the existing customer comes back after a year then they just re-scan the old inputs.

This is the action of "closing" out the application. Closing out should also involve them marking their decision (approve/deny) so that is captured in the final output PDF download.

We can then just hold closed applications for a small amount of time (30 days?) mainly for our developer support if needed to review an issue.

---

Guarantees:
* Username / passwords for all users
* High-grade encryption on all connections and stored data
* General PCI compliance (12 points -- https://www.nerdwallet.com/article/small-business/pci-compliance)
* All closed applications destroyed after 30 days
* Open applications retained 30 day max (keep them fresh)

Options:
* Source IP matching (user must originate from bank branch network)
* 2-factor authentication
* Multiple user levels for different access roles

Additional Notes:
* "Application data may be used to evaluate and improve the Diametrix FAS system"
