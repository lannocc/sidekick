# Proposal: Implementing Pipes and I/O Redirection

### Introduction

With the foundation of an advanced shell parser in place (as proposed in `doc/iosk/proposal/parser.md`), the next logical evolution for the IOSK command-line interface is the implementation of standard UNIX-style pipes (`|`) and I/O redirection (`>`, `>>`).

This feature is fundamental to the UNIX philosophy of small, composable tools. It will allow both human and AI users to chain commands together, creating powerful, on-the-fly data processing workflows. Supporting output redirection is equally critical, enabling the capture of command output to files for logging, analysis, or later use.

This proposal outlines a strategy for integrating these features into the IOSK kernel, transforming the shell from a simple command executor into a dynamic and powerful interactive environment.

### Core Concepts

1.  **Output Redirection**: This mechanism allows the user to direct the standard output of a command to a destination other than their console.
    *   **`>` (Overwrite)**: Creates or truncates the target file and writes the command's output to it.
    *   **`>>` (Append)**: Appends the command's output to the end of the target file, preserving its existing content.

2.  **Pipes (`|`)**: This mechanism connects the standard output of one command directly to the standard input of another, allowing for sequential processing of data. For example, in `$ ls /bin | search .py`, the list of files generated by `ls` is "piped" to the `search` command, which then filters that list for its specific term.

### Implementation Strategy

The core of this implementation will reside in the `IOSK.call` method within `src/iosk/kernel.py`, building directly upon the tokenization and expansion stages of the new shell parser. The key is to make the `Context` (io) object's input and output streams configurable on a per-command basis.

#### 1. Pre-processing the Command Pipeline

After the initial tokenization, the `call` method will scan the token list for redirection and pipe operators. This will split a single command line into a "pipeline" of one or more command segments.

*   **Example**: `$ ls /bin | search .py > /home/beta/scripts.txt`
*   **Pipeline**:
    *   Command 1: `['ls', '/bin']`
    *   Pipe: `|`
    *   Command 2: `['search', '.py']`
    *   Redirect: `>` to `/home/beta/scripts.txt`

#### 2. Modifying the `Context` for Pluggable I/O

The `Context` class (`src/iosk/io.py`) is central to this effort. We must introduce explicit standard input and standard output streams that can be temporarily replaced.

*   **Standard Output**: The `io.output()` method currently sends data directly to the user's device (`os.send`). We will modify it to write to a configurable stream. We can add an attribute, `io.stdout`, which can be a file handle, an in-memory buffer, or the default console writer.
*   **Standard Input**: We will introduce a new `io.stdin` attribute. This will typically be `None`, but for a piped command, it will be an in-memory buffer (`io.StringIO`) containing the output of the previous command in the pipeline.

#### 3. Handling Redirection (`>` and `>>`)

When the kernel's pipeline processor detects a redirection operator:
1.  It removes the operator and the subsequent filename from the token list.
2.  It opens the target file using `io.os.box()` for sandboxing and the appropriate mode (`'w'` for `>` or `'a'` for `>>`).
3.  It configures the `io.stdout` for the final command in the pipeline to be the handle of this opened file.
4.  After the command completes, the file handle is closed. The user sees no output on their screen, only the next command prompt.

#### 4. Handling Pipes (`|`)

When the kernel detects a pipe operator, it will execute the pipeline segments sequentially:
1.  **For the first command (`ls /bin`)**:
    *   An in-memory buffer (e.g., `pipe_buffer = StringIO()`) is created.
    *   A temporary `io` context is prepared where `io.stdout` is set to `pipe_buffer`.
    *   The command is executed. All of its output is captured in `pipe_buffer`.

2.  **For the second command (`search .py`)**:
    *   `pipe_buffer.seek(0)` is called to reset the read position to the beginning.
    *   A new temporary `io` context is prepared where `io.stdin` is set to `pipe_buffer`.
    *   The command is executed. Its logic will now read from `io.stdin` instead of a file on disk.
    *   The output of this second command goes to the default destination (the console) or to a file if it is also redirected.

#### 5. Refactoring Commands to Read from `stdin`

This new capability requires that commands be aware of `stdin`. Commands that can process file content (like `wc`, `search`, `head`, `tail`) must be refactored to check for piped input if no filename argument is provided.

**Example: Modifying `bin/wc.py`**

The `iocall` for `wc` would be updated as follows:
```python
# new iocall for bin/wc.py
async def iocall(io, argv):
    content = None
    filename = argv[0] if argv else ''

    if filename:
        # Standard behavior: read from a file
        content = await io.os.get(io, filename)
    elif hasattr(io, 'stdin') and io.stdin:
        # New behavior: read from the standard input pipe
        content = io.stdin.read()
    else:
        await io.error('wc: requires a filename or piped input')
        return

    if content is None:
        return # Error already printed by io.os.get or above

    lines = content.count('\n') + (1 if content.strip() else 0)
    words = len(content.split())
    chars = len(content)

    await io.print(f"{lines}\t{words}\t{chars}\t{filename if filename else ''}")
```

### Conclusion

Implementing pipes and redirection is a critical, high-impact enhancement for IOSK. It elevates the shell from a simple command runner to a sophisticated data processing environment. This functionality will:
*   **Increase Power and Flexibility**: Enable complex, multi-step operations in a single line.
*   **Promote Tool Composability**: Reinforce the UNIX philosophy of creating simple tools that work together.
*   **Unlock Advanced Automation**: Provide AI agents with the necessary tools to perform more complex file and data manipulation tasks without needing to write monolithic scripts for every operation.

This feature is a cornerstone for building a truly capable and intelligent conversational operating system.
